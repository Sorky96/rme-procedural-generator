# Ręczne skrypty G0

`--resources` runnera i verifiera dialogu oznacza bazowy pomiar procesu oraz przerw GUI: po trzy Preview/Validate/Cancel dla 100×100 i 500×500. Cancel jest wykonywany po gotowym wyniku; to nie test anulowania w trakcie generowania. [Scenariusz, dane i ograniczenia](../G1_RESOURCES.md). Nie łączyć z `--matrix` ani `--selection-only`.

Nowy `--selection-only` runnera/verifiera dialogu oznacza wyłącznie sparse-selection UI regression, bez 500×500. `--matrix` wymaga teraz także `MATRIX_HISTORY_GUIDANCE_PASS`, `MATRIX_HISTORY_RETRY_PASS` i `MATRIX_SELECTION_PRESENTATION_PASS`. Historyczne wyniki pozostają dowodami swoich wersji; nie należy ich relabelować bieżącym verifierem. [Zakresy i odtworzenie](../G1_DIALOG_UX.md).

Przełącznik `--matrix` runnera i verifiera dialogu uruchamia `test_procedural_dialog_matrix.cpp`: GUI 500×500, sparse selection i odmowy. Wymaga rzeczywistych wejść UI oraz wystarczającego limitu Undo w prywatnym profilu; [pełny scenariusz](../G1_DIALOG_MATRIX.md).

`g1_run_dialog_probe.py` + `test_procedural_dialog.cpp` obserwują rzeczywisty natywny dialog; wymagają wykonania poleceń GUI. `g1_verify_dialog_probe.py` sprawdza aktualność binariów/obiektów/źródeł i curated assets. [Scenariusz, screen i ograniczenia](../G1_DIALOG.md).

Normalne GUI bez modułu testowego: `g0_run_rme_snapshot.py OUTPUT FIXTURE PROFILE_DATA CONFIG --house-gui` kopiuje kanoniczny EXE do nowego prywatnego katalogu i czeka na ręcznie obserwowane Add/Undo/Redo/Undo oraz zwykłe zamknięcie. `--house-gui-case close-fixture` zamiast tego sprawdza protokół otwarcia/zamknięcia/ponownego otwarcia fixture, poprawną kartę i odpięcie palet. Obserwacje trzeba zapisać do `run/house-ui-observation.json` przed zamknięciem procesu. Runner sprawdza manifest EXE, kod wyjścia, obserwacje i hashe wejść. `--verify-existing-house-gui` weryfikuje już zakończony przebieg bez restartu i wymaga `observed-exit.json`. Timeout pozostawia PID; sam w sobie nie zezwala na ponowne uruchomienie. Wyniki i dokładne granice dowodu są w [TEST_PLAN.md](../TEST_PLAN.md).

## Aktualny BlackTek z Zones

## Publikacja przy istniejącej historii

`g0_rme_queue_allocation_probe.cpp`: buduj przez `g0_build_rme_snapshot.py OUTPUT --source docs/procedural/smoke/g0_rme_queue_allocation_probe.cpp`, uruchamiaj przez `g0_run_rme_snapshot.py OUTPUT FIXTURE PROFILE_DATA CONFIG --queue-allocation` na nowym prywatnym run. Testowe podklasy istniejących wirtualnych fabryk uzbrajają scalar `operator new` po commit właściwej akcji, przy wejściu do publikacji batcha. Cztery scenariusze: wzrost deque, limit liczby wpisów, merge z istniejącym Redo oraz limit pamięci. Merge wymuszany jest oknem timestamp w podklasie testowej, bez zmiany zegara systemowego. Przy odmowie mają pozostać identyczne wpisy/etykiety/indeks i licznik pamięci; istniejące Redo oraz Undo są wykonywane, nie tylko odczytywane. Sukces sprawdza dotychczasową politykę przycinania; obecne jednorazowe przycięcie liczby wpisów nie jest dowodem ścisłego budżetu. Po zamierzonym usunięciu starej historii fixture przywracany jest jawną akcją zawierającą pełny snapshot pola, przed niezależnym porównaniem. Setter AID 0 nie zastępuje odtworzenia nieobecnego atrybutu. `clear()` musi wyzerować także licznik pamięci. Nie zaliczać tego jako wszystkich wyjątków wewnątrz Action::commit ani wizualnego GUI; stderr i ograniczenia zachować.

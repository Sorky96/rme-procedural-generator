# D4: private memory across repeated Preview cycles (2026-11-19)

The criterion was recorded in [G6_METRICS.md](G6_METRICS.md#d1-and-d4--window-close-and-preview-memory) in commit `04b03de`. This report covers measurement and diagnosis. The production code was unchanged.

## What was run

The `tests/test_procedural_dialog_leak.cpp` probe and `docs/procedural/smoke/g1_run_leak_trend.py` runner use the settings from the 2026-11-06 series in [G1_GATE_STATUS.md](G1_GATE_STATUS.md#200-cycle-run-2026-11-06). Each run uses a 500×500 area, two warm-up cycles, a one-second wait after the dialog closes, and one sample per cycle. Each cycle opens the dialog from the menu, starts Preview, cancels it while it runs, starts Preview again, validates, and closes with Cancel.

The probe queues events. Native user input was outside the test scope. The client profile is `g0-reference-profile-20261030` (10.98, BlackTek). The build is from tree `04b03de` in the worktree.

Diagnostic changes:

- **G6 dialog alignment.** The dialog now shows “Generating candidate…” and “Selected #…”. It reports the tile count after Validate. The probe accepts both generations of status messages and checks the count in the Validate status. Before this adjustment, all four runs stopped in cycle 1 with `Preview did not start`. Those runs were removed from the results.
- **Candidate count.** The probe records `LEAK_CANDIDATE_COUNT`. The spinner held N = 4 but was disabled because the dialog used neither Natural surface mode nor a style profile. Each Preview generated one candidate, as confirmed by “Generating candidate 1/1”.
- **`--heap` mode.** After each process sample, the probe records total `MEM_PRIVATE` commit from `VirtualQuery`, `HeapSummary` for all process heaps and separately for the CRT heap (`_get_heap_handle`), and `HeapWalk` counts of busy, free, and uncommitted CRT heap bytes in `heap-trend.csv`. It records a histogram of busy CRT blocks by `floor(log2(size))` in `heap-buckets.csv`.

  After the last cycle, the probe calls `HeapCompact` on the CRT heap and takes another sample. The first version walked all five process heaps and exited with code −1 when sampling cycle 2. `wxHandleFatalExceptions` catches the SEH exception. The final version walks the CRT heap and uses `HeapSummary` for the other heaps. Both calls are wrapped in `__try`. The `faults` counter was zero in all runs. Each heap measurement took at most 55 ms.
- **Analysis.** `docs/procedural/smoke/g6_d4_analyze.py RUN...` computes the summary. It reproduces the G1 values for the older `g1-leak-200-20261106` series, with a slope of 0.31 MiB/cycle and a plateau difference of 8.61 MiB.

In the commands below, PY stands for `py -I -X utf8` and PROFILE for the main checkout's `local-data/procedural-smoke/g0-reference-profile-20261030`.

## Diagnosis

1. **Growth after warm-up.** Private memory after the dialog closes rises by about 70 MiB over 200 cycles. Almost all growth occurs in cycles 3–100. Growth then approaches zero through cycle 200 and satisfies the supplemental plateau check.
2. **Active allocations.** Busy bytes in Win32 heaps stay within 0.03 MiB over 200 cycles (roughly 150 B per cycle and 61 blocks). The measured busy blocks account for little of the growth in private memory.
3. **Allocator reserves.** About 53 of 70 MiB is committed CRT heap memory outside busy blocks, including free blocks and segment fragmentation. `HeapCompact` retains it, consistent with fragmented free blocks between live allocations below the decommit threshold. Reserve growth slows and levels off after around 100 cycles. The other 17 MiB is private commit outside Win32 heaps. Possible sources include GL driver memory, direct `VirtualAlloc` calls, thread stacks, or large-block allocations. This category levels off after around 50 cycles. In the 30-cycle heap run, it fell by 24.8 MiB while the CRT reserve grew, so shifts between the categories are possible.

The measurements show stable active allocations in Win32 heaps. Higher private memory comes from CRT heap reserve growth and fragmentation, plus unattributed commit outside the heaps that levels off. The criterion from `04b03de` requires more evidence than growth in private memory to identify a leak.

## Diagnostic limits

- Sampling occurs one second after closing the dialog. Peak memory during Preview was outside the measurement.
- The probe walks only the CRT heap. For the four other heaps it collects `HeapSummary` totals. Their allocations stay near 0.1 MiB.
- Whether `HeapWalk` and `HeapSummary` count free LFH blocks as busy remains unverified. If they do, active allocations include the LFH cache. The measured total stays stable either way.
- Commit outside the heaps, about 300–340 MiB, was left unattributed. The investigation used no ETW/xperf, UMDH, or allocation stack traces. Leaks in GL driver memory, resources outside the heap, or GPU memory remain possible.
- Each 200-cycle variant ran once. Statistical analysis is outside the report scope. The two 30-cycle runs had slopes of 1.00 and 0.37.
- G6 added candidate series, ranking, and similarity since 2026-11-06. The effective N was 1. The G1 comparison uses matching probe settings across different versions of the production dialog.
- Coverage is limited to probe-driven events, 500×500 areas, and N = 1.
- A future change such as reusing Preview buffers to reduce fragmentation would need separate acceptance criteria.

## G1 update: shared preparation budget, 2026-11-02

## C++ and Lua boundary

Client data set used in this session: `C:\repo\ProjectSorky\otclient\data\things\1098`. DAT/SPR parsing is correct, but reference tests found a different mapping from standard `data/1098/items.otb`. The smoke test must verify the existing `1098-BlackTek` (`dat_only`) profile instead of assuming the standard `10.98` profile is compatible from signatures. `ItemDefinitionResolver::resolveDatOnly` (`source/item_definitions/core/item_definition_resolver.cpp:249`) starts with identical server/client IDs and applies XML mappings; `VersionManager::LoadCanonicalAssets` selects this mode from the profile. Details and hashes: [TEST_PLAN.md](TEST_PLAN.md).

**G0 decision, 2026-11-01:** generator core, snapshot, resolver, and commit in C++; Lua optional for presets, configuration, and demonstration. This is the selected G1 responsibility boundary, not a claim that the generator is implemented. Test rationale: repeatable noise samples and selected algo/geo tests confirm that algorithms can be reused but do not control brush RNG; Draw/Lua/Draw confirmed history separation, while reproductions of an ignored callback error and an untracked setter showed that the Lua API alone was not an atomic-commit contract. Corrected callbacks, references, and the setter/method matrix passed the described regressions, but still do not prove a strong allocation-exception guarantee or isolated Preview. Therefore the existing demonstrator will not be the production commit path. Evidence and limitations: `TEST_PLAN.md`, G0-06/G0-07, noise/algo/geo attempts, the 17-setter matrix, and `g0-item-methods-20261101`.

Do not run existing Lua state or GUI managers in the worker. Lua configuration must be validated and copied into core data before work starts; live map references must not cross into the worker. Evaluate extracting needed algorithms from existing `noise`, `algo`, and `geo` only at their first real use. The open adapter decisions below remain tasks before its G1 implementation; they do not change the selected language boundary.

`scripts/terrain_generator_demo.lua` is orientation material: it has hard-coded IDs, uses direct tile mutations, and has separate decoration randomness. Do not extend it into a production generator before safety tests.

Confirmed library-level risk: `transaction` invokes `sol::function` and does not check the callback result. `source/lua/lua_sol_config.h` enables `SOL_ALL_SAFETIES_ON`. Context7 indicates that protected-call errors should be detected through the `valid()` result: [Sol2 documentation](https://github.com/ThePhD/sol2/blob/develop/documentation/source/api/protected_function.md). A local MSVC probe compiled with the project configuration header and installed Sol2 3.5.0#1 / Lua 5.5.0#1 confirmed the alias `sol::function = sol::protected_function`: the callback incremented and called `error()`, while `func();` returned without an exception; explicit checking of the second call showed an invalid result. Result: `returned_without_throw=true`, `counter_after_ignored_result=1`, `checked_call_failed=true`, code 0. Probe source and command: [TEST_PLAN.md](TEST_PLAN.md).

Confirmation on a real RME map, 2026-10-27: `g0_error_probe.lua` changed one tile and called `error()` in the callback. The outer `pcall` reported success, the tile remained, and the field count increased from 400 to 401. The final diagnostic assert reported rollback FAIL. One manual Undo reverted the change and a second verifier confirmed the original 400 fields. Thus a transaction with an error enters history and does not provide the required rollback. Plan result handling as a separate small G0-B integration PR with a test, rather than treating the current wrapper as a ready generator safety boundary. Scripts and exact scope: [TEST_PLAN.md](TEST_PLAN.md).

New reproduction after G0-B: the direct `Item.actionId` setter in `lua_api_item.cpp` does not call `markTileForUndo`, so on an existing tile a callback failure leaves the AID change and success does not append an action. `getTileItems`, the `Tile.ground` getter, and `addItemToTile` expose `Item*` pointers to Lua; binding the correct current tile to the mutation requires a design covering containers, removal, and changes after Undo/Redo. Do not add a new `Tile` layout or a full map scan as a side effect of the fix. Attempt details and the second Save As blocker: [TEST_PLAN.md](TEST_PLAN.md).

G0-C — further refactoring scope: items also reach Lua through `getItemAt`, `getTopItem`, `getWall`, `getTable`, `getCarpet`, and the `LuaScriptManager::updateMapOverlayHover` callback. `Tile.removeItem`, `Tile.moveItem`, `Tile.ground` assignment, and `Selection.add/remove` accept an item argument; all these paths must work with the new representation. Lua also receives raw `Tile*` values that rollback can invalidate. An item index, pointer address, or `Map::getGeneration()` alone does not prove identity after tile replacement, removal, or address reuse. Before wiring setters, an invalidation or reference-resolution mechanism is needed that covers these events without increasing every `Tile`'s size; tests must check references obtained before a transaction, after Undo/Redo, removal and reinsertion, and map close/tab switching. A test result for a raw pointer after object destruction may be a crash — run this part only on an isolated fixture after a safe handle is implemented.

Identity registries and destruction notifications for `Item` and `Tile` were prepared without adding fields to those objects. The registry protects its own structure from concurrent notifications, but access to the object itself must still be serialized with its destruction. The unit test covers address reuse, two registries, and unregistering during notifications from a second thread. The mechanism is not yet connected to Lua bindings and by itself does not provide mutation tracking or distinguish the current tile from one retained in Undo history.

The Sol2 version used by this build stores a raw pointer in userdata when it is created. Test `test_lua_object_registry_sol` showed that a `unique_usertype_traits` specialization with a handle does not force rechecking when a property is read: after registry invalidation, Lua still reads the previously stored address of the live object. Therefore this specialization must not be used as a lifetime safeguard; bindings must accept the reference object itself and resolve it on every access. The test intentionally does not free the observed object to avoid undefined behavior.

`SpatialChangeTracker::getGeneration()` counts dirty-area marks, including those from `Tile::modify` and `BaseMap::swapTile`; it is useful for invalidating the render cache but is not a lifetime counter for an individual object. Conservatively invalidating every handle after each counter increase would break, among other things, repeated setters on one item in a transaction and references to other tiles. Comparing addresses alone after a change still permits address reuse. G0-C must therefore distinguish object identity from map generation and account for moving an item between tiles; the existing counter must not be treated as a ready solution.

## Proposed G1 flow

G0-B update (2026-10-27): the wrapper explicitly accepts `sol::protected_function`, checks `protected_function_result::valid()`, and throws `std::runtime_error` containing the Sol2 message on error. Existing exception handling invokes rollback and passes the error to Lua. Snapshot, commit, and rollback implementations were not changed. Regression in `lua_tests/test_transaction_rollback.lua` passed on the new EXE: three errors and six mutations rolled back, messages preserved, and no new history entries after errors; two successful transactions were separated in Undo/Redo. This closes the specific ignored-callback bug, not the remaining atomicity and metadata risks from the audit.

1. Main thread: bind the concrete editor, assets, mask, and halo; check the budget and consistently capture data.
2. Worker: owned flat semantic data and controlled RNG streams; no GUI or live-tile references.
3. Prepare the concrete diff on an isolated map: reuse brush and border rules. Initially do this on the main thread until asset/brush safety in a worker is proven. Preparation time and memory must be measured.
4. Validate the concrete result: IDs, footprints, protection, bounds, and traversability. Preview retains prepared variants and does not reroll them at Commit.
5. Main thread: recheck snapshot, identity, and assets, then apply through a minimally extended `DrawOperations` contract plus existing `Action`/`Change`/`ActionQueue`.
6. Undo/Redo restores saved states. Save through the existing editor workflow. No changes to OTBM format, `Tile` layout, or vendored code.

This flow is a design, not a list of existing APIs. The decisions below must be tested before signatures are chosen.
